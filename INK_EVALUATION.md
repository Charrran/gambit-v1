# Should Gambit move story authoring to ink?

**Recommendation: not for Episode I as it stands. Revisit when there are several episodes, real branching, or writers who are not developers. If you do it, ink should own text and choice availability only; Python keeps everything multiplayer.**

## What Gambit's story actually is today

* **Linear spine.** 37 beats in a fixed order (`MASTER_BEATS`). Every choice on a beat leads to the same next beat (`seed_db.py:60`). Choices change *state*, not *position*.
* **Branching by availability.** Choices and interrogations appear or disappear on state conditions (`requires`/`blocks`/`trigger`). Each visible choice adds integer `effects` (15 axes) and `lanes` (9 lanes).
* **Four actors, one story.** Spotlight beats belong to one role. Polls are decided by four votes. Interrogations involve two roles, one of whom answers. The ending comes from the whole table's decisions (`resolve_lane`, with per-decision pressure since this change).
* **Text is a starting point.** The LLM Director rewrites every option's text before players see it (`ai_engine.generate_spotlight_turn`/`generate_poll_turn`). Authored text is the fallback, and with the retired model IDs it is currently what players see.

ink's strengths are (a) authoring branching prose comfortably, with knots, stitches, diverts, gathers and weave, and (b) evaluating conditional choices and text variation. Gambit uses (b) heavily and (a) barely, and its prose is mostly regenerated by the LLM.

## Python runtime options

inkle maintains runtimes for C# and JavaScript (inkjs) only. Python options are community projects: a pure-Python port, bindings to the Rust *blade-ink* runtime, or running inkjs out of process (Node subprocess or an embedded JS engine). Check each candidate's ink-version compatibility, maintenance activity and state save/load support before committing. A runtime that cannot save and restore story state as JSON is unusable here (see below). Bundling Node to run inkjs is the most compatible route, but adds a second language runtime to the Docker image.

## Where four-player shared state would live

ink assumes **one reader with one cursor**. Gambit has four players acting on one shared state, so the authority has to stay outside ink:

| Concern | Owner | How |
|---|---|---|
| Axes, lanes, `lane_pressure`/`lane_spread`, flags, player profiles, votes, spotlight counts | **Python `GameState` in Redis** (unchanged) | as today |
| Beat order, spotlight role, interrogation pairing, poll tally and tie-break, top-3 ranking (`select_reactive_choices`) | **Python** | ink shows *all* eligible choices; it has no notion of a 4-way vote, whose turn it is, or "show the best 3" |
| Beat and interrogation text, choice text, conditional availability, text variation | **ink** | one knot per beat or interrogation |
| Effects of a choice | **ink tags read by Python** (`# effect saraswathi_influence +2`, `# lane saraswathi_ascendancy +1`) | keeps effects as deterministic data the simulator can read; do **not** apply effects as ink variable assignments, or state would live in two places |
| ink runtime state | **Python** | either (a) build a fresh story per scene, push the current axes and flags into ink variables (or expose them via `EXTERNAL` functions bound to Python), divert to the beat's knot, read `currentChoices`, then discard; or (b) store the ink save-state JSON in the Redis session next to `GameState`. Because the spine is linear and all state is in Python, (a) is enough and avoids two persisted states drifting apart. |

A scene would run like this:

1. `prepare_scene` syncs `GameState` into ink.
2. It diverts to the knot and reads the eligible choices plus their tags.
3. The existing Python code ranks them, picks the actor or opens the poll, and calls the LLM.
4. `apply_choice` resolves the vote, applies the tag effects, and records lane pressure.
5. `ChooseChoiceIndex` is called on ink only if ink's own text needs to continue.

## How much code would change

| Area | Change | Size |
|---|---|---|
| `app/design/content.py`: `MASTER_BEATS`, `INTERROGATIONS` (≈450 of 833 lines) | rewritten as `.ink` files | large, mechanical; a converter script is feasible |
| `content.py` helpers (`normalize_choice`, `choice_conditions_match`, `_eval_condition`, `interrogation_trigger_passes`, `option_available`) | replaced by an ink adapter (≈150 lines new) | medium |
| `scene_engine.py` (575): `_reactive_payloads_for_beat`, the interrogation branch of `prepare_scene` | source choices from the adapter instead of Neo4j edges plus content dicts | medium |
| `interrogation_engine.py` (204): `build_interrogation_payloads` | read options from ink | small–medium |
| `graph_store.py` (90), `seed_db.py` (110), `app/models/graph.py`, Neo4j | redundant for Episode I; the graph only adds IDs and roles to a linear chain | remove, or keep only as a chapter index |
| `choice_resolver.py`, `resolve_lane`, `lane_opportunity`, `ending_engine.py`, `ai_engine.py` | unchanged if effects arrive in the same payload shape | none |
| `main.py`, WebSocket loop, `state.py`, Redis, frontend | unchanged | none |
| `sim/` harness and tests | `FakeGraph` replaced by the adapter; the equivalence and regression tests carry over | small |

In total, roughly **35–40% of the backend game-logic code** would be touched, plus a full content conversion. Infrastructure and frontend are untouched.

## Benefits and costs

**For ink**

* Writers get Inky (live preview, syntax checking) instead of editing Python dict literals. Conditions read naturally (`{saraswathi_influence >= 4}`).
* Text variation (`{&…|…}`, sequences, conditional sentences) would give authored text more life when the LLM is unavailable, which is currently always.
* It becomes worth it once episodes truly branch (different beats, not just different options), because that is where ink's structure pays off.
* Neo4j could be dropped for Episode I: one less hosted dependency, and the one that is currently gone.

**Against ink (now)**

* The spine is linear, so most of ink's structural power goes unused.
* The LLM rewrites choice text, which halves the value of nicer authored prose.
* No first-party Python runtime: maturity and compatibility risk, or a Node dependency.
* All the hard parts stay in Python either way: the multiplayer rules, the 4-way poll, top-3 ranking, effects, and ending resolution. The balance work in this repo (pressure-based endings, regression tests) is independent of the authoring format.
* There is a real risk of two sources of truth for conditions and effects unless the tags-only rule is enforced.

## If you do it: a low-risk path

1. Pick the runtime by testing save/load and `EXTERNAL` function binding on a spike.
2. Write a converter from `MASTER_BEATS`/`INTERROGATIONS` to `.ink`, with conditions as choice guards and effects/lanes/priority/tags as ink tags.
3. Convert **one chapter**. Use the existing `tests/test_equivalence.py` pattern to prove the ink adapter offers exactly the same choices with the same effects as `content.py` for recorded sequences, then convert the rest.
4. Keep `tests/test_balance_regression.py` green throughout; the ending distribution must not move.
